# Release signing & key custody

What "qdistro v1" *is*, cryptographically: a **signed source manifest**. There
is no per-org release tag and no monolithic image (see `03-release-engineering`,
D1/D10). The manifest names — for each source repo — the exact commit the
release was built and tested from, optionally its tag, its built-artifact
digest, and the signer. The bootstrap refuses to clone or build any of it as
root until that manifest's signature verifies against a published key.

This page is the one-page custody record the v1 release blocks on.

## The release manifest

`scripts/install/source-manifest.txt` — one line per repo, generated by
`scripts/install/gen-source-manifest.sh`:

```
<repo>\t<40-hex-commit-sha>[ tag=<tag>][ artifact=<algo>:<hex>][ signer=<id>]
```

- **commit sha** (field 2) is the cryptographic anchor and the only field the
  legacy pin path (`manifest_pin` / `verify_repo_pin`) reads. The 2-field form
  `<repo> <sha>` stays valid forever — the trailing `key=value` fields are
  additive and order-independent.
- **tag** — the repo's release tag. If present, `verify_repo_pin` requires the
  tag to resolve to the pinned commit (a mismatch is tamper-evidence and is
  fatal; an absent tag in a shallow clone is a warning — the commit pin still
  holds).
- **artifact** — `sha256:<64hex>` or `sha512:<128hex>`, the digest of the
  built artifact for that repo. Carried for the build/upgrade story to verify
  against; not yet enforced against built binaries by the bootstrap.
- **signer** — the release signer identity recorded per line, advisory only
  (it lives *inside* the signed document, so it documents intent; it is not a
  trust anchor). The authoritative signer check is `QDISTRO_RELEASE_SIGNER`,
  matched by the verifier against the actual gpgv signing-key fingerprint (not
  against this field) — see below.

Generate a populated, signed-content manifest for a release:

```sh
scripts/install/gen-source-manifest.sh \
    --repo-root /opt/qdistro-src --tags --require-tags \
    --signer 0xRELEASEKEYFINGERPRINT \
    --artifact qdwin=sha256:... --artifact qdshell=sha256:... \
    -o scripts/install/source-manifest.txt
```

(Refuses a dirty or untagged tree; `--lint` re-checks an existing file.)

## Signing & verification flow

1. Generate the manifest (above) from clean, tagged checkouts.
2. Detach-sign it with the **release signing key**:
   `gpg --local-user 0xFINGERPRINT --detach-sign source-manifest.txt`
   → `source-manifest.txt.sig`.
3. Publish, alongside the bootstrap: the manifest, the `.sig`, and the gpgv
   keyring of release public keys
   (`gpg --export 0xFINGERPRINT > qdistro-release-keyring.gpg`).
4. On install, `qdistro-bootstrap.sh` runs `verify_manifest_signature`
   **before any clone or build** — at the top of `fetch_sources`, ahead of the
   `--skip-sources` early return (pre-staged sources are still root-built, so
   the gate and per-repo pin checks run for them too). In a hardened profile,
   once the manifest carries any active line it MUST verify:
   `verify-source-manifest.sh <manifest> <sig> <keyring> [expected-signer]`
   (gpgv signature, optional gpgv-key binding, + `gen-source-manifest.sh --lint`
   shape). Missing keyring/sig or a bad signature is fatal — root will not clone,
   pin-check, build, or install any source tree until the manifest verifies (the
   gate covers the *source*; the privileged bootstrap script itself runs before
   it and is not verified by it). The manifest + sig are copied into a root-owned
   0700 dir and
   verified there, and every later pin/field read comes from that verified copy
   (closes the TOCTOU window when the bootstrap runs out of a user-owned tree).

The unsigned, all-commented stub that ships in-repo has no active pins, so the
gate is a no-op and the per-repo `verify_repo_pin` still fails loud ("no
manifest pin") — a release must populate *and* sign the manifest to install on
a hardened profile. The `dev` profile skips the gate entirely (shallow branch
clones, disposable VMs).

Overrides: `--release-keyring` / `QDISTRO_RELEASE_KEYRING`,
`--manifest-sig` / `QDISTRO_SOURCE_MANIFEST_SIG`,
`--release-signer` / `QDISTRO_RELEASE_SIGNER`.

## Trusting the bootstrap itself

The signed manifest authenticates the **sources**. It cannot authenticate the
**installer**: by the time `qdistro-bootstrap.sh` can check anything, bash has
already parsed and executed it and has sourced
`scripts/install/lib/qdistro-profile.sh` from the same directory. A user
who can write that directory has root the moment the operator types `sudo` —
they can edit the script, or redefine `is_dev` so every hardened gate becomes a
no-op. No check inside the script can undo that.

So this is a **distribution precondition, not a runtime check**:

- The bootstrap, `lib/qdistro-profile.sh`, `verify-source-manifest.sh`, the
  manifest and the release keyring must reach the target through an
  **authenticated channel** — a signed package/image, or a download whose
  signature the operator verifies against the published release fingerprint
  **before** running it — and must live in a **root-owned, non-group/other-
  writable directory** when it is run.
- `qdistro-bootstrap.sh` enforces the second half only (hardened profiles run
  `assert_trusted_tree "$SCRIPT_DIR"` right after `require_root`, which refuses
  a user-writable installer directory loudly and early, and protects the later
  re-reads of the verifier/keyring/manifest). It does **not**, and cannot,
  enforce the first half.
- Corollary: never `sudo` a hardened install directly out of a developer
  checkout under `/home/<user>`. Install from the release artifact, and let the
  installer clone the sources itself into a root-owned `--repo-root`
  (`/opt/qdistro-src`).

The same reasoning is why the installer refuses to root-build from any source
tree it cannot vouch for, and why its refusal message does **not** offer
`chown -R root:root` as a remedy: current ownership is used as a proxy for
provenance, and chowning a tree an unprivileged user could write makes it pass
the check without making its `.git/config`, its ignored build state or its
symlinks any more trustworthy. A fresh clone into a root-owned directory is the
only remediation that removes the attacker's content.

## Key custody

- **Generation.** One Ed25519 (or RSA-4096) OpenPGP release signing key per the
  release-engineering owner. Generated offline; the **private key never touches
  a build host or CI**. Signing of the manifest is a deliberate, local step.
- **Storage.** Private key on a hardware token (or an offline, encrypted
  keystore) held by the release owner. The passphrase is not stored with the
  key. No copy on any internet-connected build machine.
- **Publication.** The *public* key is published as
  `qdistro-release-keyring.gpg` next to the bootstrap on the install site, and
  its full fingerprint is printed on the install page and in this doc once a key
  exists. Users verify the bootstrap+manifest against this fingerprint.
- **Rotation.** Routine rotation at a fixed cadence (or on owner change):
  generate the new key, sign the new public key with the old one (chain of
  trust), publish both fingerprints during an overlap window, then sign the
  next release manifest with the new key and retire the old from the keyring.
- **Revocation.** Keep a pre-generated revocation certificate offline. On
  suspected compromise: publish the revocation, pull the compromised key from
  `qdistro-release-keyring.gpg` on the site, and re-sign the current manifest
  with a fresh key. Because the keyring is fetched at install time, removing the
  key there is what actually stops new installs from trusting it — so the site
  keyring is the revocation control surface, not just the per-key cert.

### Status

The signing/verification machinery and this custody policy exist; the v1 release
key itself is **not yet generated/published**. v1 blocks on: generate the key,
publish the keyring + fingerprint, sign the RC manifest, and confirm a hardened
clean-room install verifies it (`06` clean-room install follows the install
page). See `03-release-engineering.md` R1/R2.
